# Анализ перед редизайном UI

Дата анализа: 26 сентября 2026 г.

## 1. Цель и источники

Документ фиксирует состояние приложения перед полноценной перестройкой интерфейса и служит основанием для `UI_REDESIGN_PLAN.md`.

Проанализированы:

- `docs/design/reference/` — три референсных снимка стартового экрана, корня результата и вложенного каталога;
- `docs/design/UI_DESIGN_SPEC.md` — обязательное визуальное направление и критерии редизайна;
- `docs/design/UX_UI_SPEC.md` — каноническое UX-поведение, состояния, accessibility и performance budgets;
- `docs/requirements/SRS.md` — продуктовые требования;
- `docs/implementation/IMPLEMENTATION_PLAN.md` — техническая архитектура и порядок реализации;
- `docs/roadmap/STAGES.md` — заявленный статус этапов;
- фактический frontend и generated Tauri IPC-контракт.

При конфликте план исходит из SRS для функциональности, `UX_UI_SPEC.md` для поведения и `UI_DESIGN_SPEC.md` вместе с референсами для визуальной композиции. Более безопасное или более проверяемое требование сохраняется, если документы не противоречат продуктовой функции.

## 2. Что задают референсы

### 2.1. Общая композиция

Все три снимка используют одну desktop-композицию:

- постоянный sidebar шириной примерно 16–17% окна;
- header и workspace внутри отдельной основной области;
- темно-синий фон с более насыщенным синим sidebar;
- тонкие разделители, компактные строки и умеренные скругления;
- bottom bar как часть рабочего контекста, а не отдельный footer страницы.

Референсы сняты примерно в разрешении 2566×1430. Их нельзя переносить пиксель-в-пиксель: целевой интерфейс должен сохранять композицию на рабочей области от 1100×700 и корректно масштабироваться выше.

### 2.2. Стартовое состояние

Первый снимок показывает:

- выбранную локацию и системные места в sidebar;
- сведения о выбранной папке слева в workspace;
- явно декоративную, приглушенную radial-графику справа;
- одну доминирующую CTA «Начать сканирование» в нижней части основной области;
- отсутствие файлового браузера до появления данных.

Декоративная radial-графика не должна выглядеть как реальные результаты. Коммерческий блок MacCleaner и брендовые элементы из референса исключаются.

### 2.3. Результат в корне

Второй снимок показывает:

- поиск и mode switcher в header;
- текущий каталог и его размер в центре header;
- компактный browser первого уровня слева;
- Sunburst как доминирующую визуализацию справа;
- breadcrumb над нижней панелью;
- disabled action, пока ничего не выбрано.

### 2.4. Вложенный каталог и выбор

Третий снимок уточняет ключевое поведение:

- каждый открытый уровень добавляет колонку;
- колонны имеют самостоятельные вертикальные границы и общий горизонтальный scroll;
- Sunburst уменьшается, но остается видимым;
- breadcrumb отражает весь путь;
- выбор синхронно виден в строках и визуализации;
- bottom action bar показывает общий размер, количество и основное действие.

### 2.5. Визуальные правила, которые нужно перенести

- высокая информационная плотность без oversized-карточек;
- один яркий primary blue для активного элемента и CTA;
- спокойные поверхности и разделители вместо множества карточек;
- размеры выровнены справа и легко сравниваются;
- цвет размера дополняет число, но не заменяет его;
- рабочая область меняется по состоянию приложения, shell остается стабильным.

## 3. Текущий стек и архитектура

### 3.1. Стек

- React 19 + TypeScript;
- Vite 7;
- Tauri 2;
- plain CSS без UI-kit;
- Vitest + Testing Library;
- generated IPC-клиент в `apps/desktop/frontend/src/api/generated.ts`;
- Rust core и SQLite за Tauri adapter.

Стек способен реализовать целевой интерфейс. Замена React/Tauri не нужна. Sunburst уже рисуется собственным SVG, поэтому внешняя chart-библиотека не требуется до результатов profiling. Для системного выбора каталога может понадобиться штатный Tauri dialog API/plugin, но добавление зависимости должно быть отдельным обоснованным контрактным изменением.

### 3.2. Текущий layout

`App.tsx` строит одну вертикальную страницу:

1. маркетинговый hero;
2. карточка состояния приложения;
3. `ScanPanel`;
4. `AnalyzerPanel`;
5. `OldFilesPanel`;
6. `HistoryDuplicatesPanel`;
7. footer.

Это прямо расходится с требуемой моделью `Sidebar + Header + Workspace + Bottom Action Bar`. Текущий layout нельзя сохранять как основу редизайна.

### 3.3. Текущее состояние frontend

Состояние распределено между крупными компонентами:

- `App` знает readiness, capabilities и активный scan;
- `ScanPanel` самостоятельно загружает volumes, стартует/отменяет scan и опрашивает прогресс;
- `AnalyzerPanel` содержит навигацию, страницы каталога, карту, категории, large files, поиск, selection и файловые действия;
- `OldFilesPanel` и `HistoryDuplicatesPanel` управляют собственными инструментами.

Такое разделение работало для последовательной страницы, но не дает shell синхронно управлять текущей локацией, режимом, breadcrumb, колоннами, визуализацией и bottom bar.

### 3.4. Фактически доступный IPC

Уже доступны и должны переиспользоваться:

- app info и capability model;
- volumes;
- start/cancel/current scan и progress channel;
- bounded scan issues;
- scan root и paginated children;
- bounded directory map с metric/depth/max children;
- large files, categories и category files;
- indexed search;
- open/reveal;
- single и batch move-to-trash;
- scan history, compare и retention;
- duplicate discovery/verification/deletion;
- old files.

Generated-контракт нельзя редактировать вручную.

## 4. Что можно переиспользовать

### 4.1. Без изменения backend-контракта

- lifecycle и защита от устаревших scan updates из `ScanPanel`;
- форматирование `BigInt`-размеров и счетчиков;
- пагинация `getChildren` и query API;
- виртуализированный renderer строк;
- bounded `getDirectoryMap` и текущие функции построения SVG-секторов;
- навигация назад/вперед как основа navigation history;
- capability-driven включение корзины и метрик;
- open/reveal и batch trash;
- категории, large files, поиск, old files, history и duplicates;
- существующие безопасные тексты ошибок и проверки browser preview.

Переиспользовать следует поведение и узкие utilities, а не текущую визуальную оболочку компонентов.

### 4.2. Что нужно выделить из монолитов

- scan lifecycle в hook/view model, доступный всему shell;
- analyzer domain state отдельно от представлений режимов;
- единый navigation state: current directory, columns, history, breadcrumb;
- единый selection state по entry id;
- общий query state для loading/empty/error/pagination;
- отдельные presentation-компоненты Shell, Sidebar, Header, Workspace, FileRow, Column Browser, Sunburst и Bottom Bar;
- инструменты History, Duplicates и Old Files в самостоятельные workspace modes.

## 5. Разрывы между целевым UX и текущим контрактом

Ниже перечислены не предположения о новых API, а подтвержденные разрывы, которые нужно закрыть до зависимой UI-реализации.

| Требуется                 | Сейчас доступно                                                  | Ограничение                                                   | Предлагаемое решение                                                                                                   |
| ------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Системный выбор папки     | только поле абсолютного пути                                     | кнопка reference не может открыть native dialog               | добавить штатный Tauri dialog boundary или подтвержденный эквивалент                                                   |
| Метаданные папки до scan  | только введенный путь и данные volume                            | нет type/created/modified/parent metadata                     | либо добавить read-only target-info command, либо явно сократить стартовую карточку до подтвержденных данных           |
| Progressive results       | progress содержит счетчики, analyzer читает только terminal scan | нельзя честно показывать дерево/карту во время scan           | отдельным контрактным этапом разрешить consistent read текущих агрегатов либо оставить progress-only до terminal state |
| Текущий путь при scan     | `ScanSession` не содержит current path                           | reference требует показывать обрабатываемый путь              | расширить progress DTO только если scanner реально знает и безопасно throttles это поле                                |
| Полные строки Large Files | `IndexedEntry` не содержит modified/category в результате        | таблица reference/UX неполна                                  | расширить специализированный DTO/query; не перегружать базовый entry без необходимости                                 |
| Расширенный поиск         | текущий вызов принимает только text                              | нет явных фильтров extension/path/category/type/size/modified | спроектировать typed search request и paginated response                                                               |
| Tooltip Sunburst          | есть path/size и вычисляемый процент                             | нет количества элементов и части metadata                     | либо добавить summary поля в map node, либо показывать только подтвержденные данные                                    |
| Permanent delete          | capability существует, IPC-команды нет                           | действие нельзя делать рабочим                                | не показывать действие до реализации FileOperationService и подтверждения                                              |
| Copy path                 | готовой команды нет                                              | нужен надежный cross-platform clipboard path                  | выбрать браузерный Clipboard API или Tauri plugin после проверки permission model                                      |
| Sidebar favorites/recent  | platform известна, стандартные пути не выдаются                  | нельзя безопасно угадывать абсолютные пути                    | добавить platform-resolved locations либо штатный path API с тестами на трех ОС                                        |
| Отключение volume         | volume DTO ограничен name/mount/filesystem/space                 | нет stable id/status/removable/read-only                      | расширять только в рамках platform metadata stage; до этого не изображать неподтвержденные состояния                   |

## 6. Главные архитектурные риски

### 6.1. Рассинхронизация представлений

Текущий Sunburst по click сразу открывает каталог, а строка использует отдельный selection. Требование различает single selection и drill-down. Если оставить две модели, browser, breadcrumb, bottom bar и Sunburst будут расходиться.

Решение: одна reducer/state machine с событиями `select`, `activate`, `navigate`, `back`, `forward`, `changeMode`; все представления являются проекциями этого состояния.

### 6.2. Column Browser и pagination

Одна колонка может содержать больше одной страницы. Нельзя загружать все дочерние элементы ради колонного вида.

Решение: каждая колонка хранит собственный page state, cursor, scroll и loading; виртуализация применяется внутри видимой колонны. Горизонтальный scroll не отменяет вертикальную виртуализацию.

### 6.3. Масштаб SVG

Текущий Sunburst ограничен глубиной 3 и `maxChildren=8`, что безопасно, но его цвета циклические, tooltip минимален, default — Treemap, а select/drill-down не разделены.

Решение: оставить bounded server aggregation, сделать Sunburst default, стабилизировать color assignment по ветви/id, ввести hover/focus/selected states и измерить render/interaction budget до увеличения числа узлов.

### 6.4. Потеря существующей функциональности

Референс не показывает Categories, Duplicates, Old Files, History и Compare. Удалять их нельзя.

Решение: основные режимы — в header; расширенные инструменты — в Sidebar/«Ещё». Каждый получает отдельный workspace, а не карточку в конце длинной страницы.

### 6.5. Опасные операции

Текущий UI использует `window.confirm` и отдельные кнопки trash в строках. Это не дает полноценного review, частичного результата и управляемого focus.

Решение: единый review flow, capability check, повторная проверка core, результат batch operation и сохранение failed selection. Permanent delete не включать, пока нет отдельного контракта.

### 6.6. Визуальная проверка

Browser preview честно не имитирует backend, поэтому одного Vite preview недостаточно для проверки всех состояний.

Решение: визуально проверять shell/empty/browser-safe состояния в preview, а реальные scan/result/delete flows — в native Tauri с синтетическим test directory. Статический fake production state не добавлять.

## 7. Разрешённые и оставшиеся расхождения документации

- Устаревшие утверждения Roadmap об отсутствии SRS и Analyzer UI исправлены 26 сентября 2026 г.
- Implementation Plan размещён по каноническому пути `docs/implementation/IMPLEMENTATION_PLAN.md`.
- Приоритет закреплён так: SRS определяет функциональность, `UX_UI_SPEC.md` — поведение, `UI_DESIGN_SPEC.md` и reference — визуальную композицию. При реальном противоречии зависимая реализация останавливается до согласования, а не выбирает источник молча.

Эти расхождения не блокируют проектирование, но должны быть исправлены до объявления этапа редизайна завершенным.

## 8. Вывод

Редизайн технически реализуем на текущем стеке и не требует нового приложения или demo-layer. Основная работа — перестройка frontend state и композиции с сохранением generated IPC и core services. Несколько целевых сценариев требуют отдельных контрактных задач; до их выполнения UI должен честно деградировать, а не использовать mock-данные или неработающие controls.
