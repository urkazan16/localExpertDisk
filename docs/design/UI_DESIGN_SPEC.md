# UI_DESIGN_SPEC.md

# Disk Space Analyzer — UI/UX Design Specification

## 1. Назначение документа

Этот документ является обязательной спецификацией пользовательского интерфейса для проекта **Disk Space Analyzer**.

Он определяет:

- целевое визуальное направление приложения;
- структуру экранов;
- правила компоновки;
- поведение основных UI-компонентов;
- требования к интерактивности;
- требования к производительности;
- правила работы с большими объемами файлов;
- требования к визуальной проверке результата;
- критерии завершенности редизайна.

Документ должен использоваться как основной источник требований для всех задач, связанных с UI/UX.

При изменении интерфейса CODEX обязан учитывать этот файл до начала реализации.

---

# 2. Главный принцип редизайна

## 2.1. Старый интерфейс не является основой нового дизайна

Текущий UI приложения считается временным.

Нельзя считать редизайн выполненным, если:

- сохранена старая структура окна;
- изменены только цвета;
- добавлен темный фон;
- заменены кнопки;
- слегка изменены отступы;
- добавлена диаграмма;
- старый layout остался практически без изменений.

Необходимо выполнить полноценную переработку:

- общей структуры окна;
- навигации;
- боковой панели;
- экранов до и после сканирования;
- представления файловой структуры;
- визуализации занятого пространства;
- нижней панели действий;
- breadcrumb-навигации;
- состояний выбора файлов;
- удаления;
- поиска и режима больших файлов.

## 2.2. Бизнес-логика должна быть сохранена

Редизайн не должен удалять уже реализованный функционал.

Допускается:

- изменять UI-архитектуру;
- разбивать старые компоненты;
- создавать новые компоненты;
- менять layout;
- менять навигационную модель;
- менять способ визуализации;
- реорганизовывать слой состояния UI.

Не допускается:

- удалять рабочие функции только потому, что их нет на референсе;
- заменять реальные данные mock-данными;
- создавать отдельный demo-интерфейс, не связанный с приложением;
- оставлять старый UI как основной.

---

# 3. Визуальные референсы

Приложенные скриншоты используются как визуальное направление.

Они задают:

- общую композицию;
- темную цветовую схему;
- вертикальный sidebar;
- крупную рабочую область;
- верхнюю панель;
- представление каталога;
- radial/sunburst-визуализацию;
- нижнюю панель действий;
- визуальную плотность;
- стиль desktop-приложения.

Референсы не требуют копирования:

- названия MacCleaner;
- логотипов;
- рекламных блоков;
- лицензионных экранов;
- кнопок покупки;
- чужих брендовых элементов.

---

# 4. Анализ текущего проекта перед изменениями

Перед реализацией UI необходимо определить:

- какой UI-фреймворк используется;
- как устроен текущий AppShell;
- как устроено состояние приложения;
- где находится логика сканирования;
- где находится модель файловой системы;
- как представлены диски;
- как представлены каталоги;
- как реализовано удаление;
- как хранятся размеры и метаданные;
- есть ли уже визуализация;
- какие существуют ограничения стека.

Перед крупным редизайном рекомендуется создать:

`docs/UI_REDESIGN_ANALYSIS.md`

В нем описать:

- текущий стек;
- текущий layout;
- компоненты, которые можно переиспользовать;
- компоненты, которые нужно заменить;
- ограничения;
- риски;
- план перехода на новый UI.

---

# 5. Проверка возможностей стека

Если текущий стек способен реализовать целевой интерфейс, нужно сохранить его.

Если конкретные элементы невозможно реализовать качественно стандартными средствами, допускается:

- собственная отрисовка;
- Canvas;
- SVG;
- OpenGL;
- custom painter;
- дополнительная библиотека визуализации;
- виртуализация списков.

Менять основной стек целиком нельзя без объективной необходимости.

Если есть техническое ограничение, оно должно быть зафиксировано в виде:

```text
Что требуется
Что позволяет стек
В чем ограничение
Какое решение предлагается
```

---

# 6. Общая структура окна

Интерфейс должен состоять из двух основных областей:

```text
┌─────────────────────────────────────────────────────────────┐
│ Sidebar │ Main Content                                     │
│         │                                                  │
│         │                                                  │
│         │                                                  │
│         │                                                  │
└─────────────────────────────────────────────────────────────┘
```

Sidebar постоянный.

Main Content меняется в зависимости от состояния приложения.

Приложение должно выглядеть как единое desktop-приложение.

Не допускается ощущение набора разрозненных стандартных контролов.

---

# 7. Общий визуальный стиль

Основное направление:

- темная тема;
- темно-синий основной фон;
- более насыщенный sidebar;
- ярко-синий основной акцент;
- светлый основной текст;
- приглушенный вторичный текст;
- мягкие разделители;
- умеренные скругления;
- компактные, аккуратные элементы;
- минимальный визуальный шум.

Примерное направление палитры:

```text
Background:         #082E47 – #0C3652
Sidebar:            #064A70 – #07587F
Selected Surface:   #0D83C8 – #1595E5
Primary:            #0A84FF
Text Primary:       #F3F7FB
Text Secondary:     #A8C1D4
Border:             rgba(80,160,210,0.20–0.35)
Danger:             #FF5A5F
Warning:            #FFB020
Success:            #31C48D
```

Значения не являются жесткими.

Разрешается корректировка для цельного визуального результата.

---

Все стили должны быть централизованы.

Не использовать случайные magic numbers по всему коду.

Нужны общие токены:

```text
colors
spacing
radius
font sizes
font weights
borders
shadows
button heights
row heights
sidebar width
animation duration
```

Пример логической структуры:

```text
spacing.xs
spacing.sm
spacing.md
spacing.lg
spacing.xl

radius.sm
radius.md
radius.lg

color.background
color.surface
color.sidebar
color.primary
color.textPrimary
color.textSecondary
color.border
color.danger
color.warning
```

---

# 9. Sidebar

## 9.1. Размер

Ориентировочная ширина:

```text
250–290 px
```

Sidebar не должен чрезмерно растягиваться на широких экранах.

## 9.2. Структура

Пример:

```text
user

Внешние диски
    Macintosh HD / системный диск
    подключенные диски

Избранные
    Программы
    Загрузки

Папки
    + Выбрать папку...
```

Названия адаптировать под ОС.

macOS:

```text
Macintosh HD
Программы
Загрузки
```

Windows:

```text
C:
Program Files
Downloads
```

Linux:

```text
/
Home
Downloads
```

Не привязывать функциональность к одному названию диска.

## 9.3. Активный элемент

Активный элемент:

- ярко-синий фон;
- белый текст;
- белая или светлая иконка;
- скругление;
- контрастное выделение.

## 9.4. Нижняя область

Не копировать рекламный блок MacCleaner.

Не добавлять:

- Купить;
- Upgrade;
- Pro;
- License;
- Очистить больше.

Если требуется заполнение нижней области, допустимо отображать:

- версию;
- краткую информацию о диске;
- статус приложения.

---

# 10. Стартовый экран

До сканирования центральная часть должна содержать:

- выбранную папку или диск;
- метаданные;
- сообщение о необходимости запуска сканирования;
- визуальный placeholder справа;
- основную кнопку действия.

Пример структуры:

```text
[иконка папки]

user

Тип:      Папка
Создан:   ...
Изменен:  ...
Место:    ...

Нажмите кнопку «Начать сканирование»,
чтобы просмотреть содержимое
```

Справа допускается:

- приглушенная radial-визуализация;
- placeholder;
- пустой круг;
- декоративная схема.

Она не должна изображать реальные данные до сканирования.

---

# 11. Основная кнопка запуска

Кнопка:

`Начать сканирование`

Должна быть основным визуальным действием.

Ориентировочные параметры:

```text
width: 280–360 px
height: 52–64 px
radius: 16–20 px
```

Расположение:

- нижняя правая часть main content;
- либо логически аналогичная область в зависимости от размера окна.

---

# 12. Состояние сканирования

После запуска интерфейс переходит в состояние scanning.

Нужно показывать:

- факт сканирования;
- текущий путь;
- количество обработанных файлов;
- объем данных;
- прогресс, если он достоверно вычисляется;
- возможность отмены, если поддерживается.

Пример:

```text
Сканирование…

/Users/user/Documents

Обработано: 18 420 файлов
Проанализировано: 8.7 ГБ

[██████████────────] 58%

Отменить
```

Если точный процент неизвестен, использовать indeterminate progress.

Главное требование:

UI не должен выглядеть зависшим.

---

# 13. Экран результатов

После сканирования структура должна меняться.

Ориентировочно:

```text
┌───────────────────────────┬──────────────────────────────┐
│ File Browser              │ Disk Visualization           │
│                           │                              │
│                           │                              │
└───────────────────────────┴──────────────────────────────┘
```

Рекомендуемое распределение:

```text
40% File Browser
60% Visualization
```

Допускается иное соотношение, если оно визуально лучше.

---

# 14. Верхняя панель результатов

Содержит:

- поиск;
- переключатель режима;
- текущий контекст;
- размер текущей папки.

Пример:

```text
[Search] [Структура папок] [Большие файлы]

user    Размер: 13.6 ГБ
```

Переключатель:

- активный режим выделен;
- неактивный выглядит доступным;
- режимы не должны выглядеть disabled.

---

# 15. Folder Browser

В режиме структуры папок отображать реальные элементы.

Пример:

```text
☐ 📁 Documents                 2.04 GB
☐ 📁 Downloads                 667 MB
☐ 📁 Projects                  420 MB
☐ 📁 Music                     105 MB
☐ 📁 Pictures                   80 MB
```

Для каждой строки:

- checkbox или иной механизм выбора;
- иконка;
- название;
- размер;
- hover;
- selected state.

Размер выравнивать справа.

---

# 16. Цветовое выделение размера

Допустимо использовать цветовую подсказку.

Пример:

```text
> 1 GB       red/orange
100 MB–1 GB  yellow/orange
<100 MB      neutral
```

Цвет не должен быть единственным источником информации.

Числовое значение всегда обязательно.

---

# 17. Навигация по каталогам

Пользователь должен иметь возможность:

- открывать папки;
- переходить глубже;
- возвращаться назад;
- использовать breadcrumb;
- переходить через диаграмму;
- синхронно обновлять визуализацию и файловую область.

---

# 18. Column Browser

Если стек позволяет, реализовать режим колонок наподобие Finder Column View.

Пример:

```text
┌────────────┬────────────┬────────────┐
│ user       │ project    │ models     │
│            │            │            │
│ Folder 1   │ models     │ file 1     │
│ Folder 2   │ src        │ file 2     │
│ Folder 3   │ reports    │ file 3     │
└────────────┴────────────┴────────────┘
```

Каждая следующая выбранная папка открывается в новой колонке.

При большом количестве колонок использовать горизонтальный scroll.

Не открывать отдельное окно для каждого уровня.

---

# 19. Breadcrumb

Обязательный элемент.

Пример:

```text
user > voice_intonation > models
```

Каждый сегмент кликабелен.

Нажатие на любой родительский сегмент возвращает на соответствующий уровень.

Breadcrumb должен синхронизироваться с:

- Folder Browser;
- Column Browser;
- Sunburst.

---

# 20. Disk Visualization

Ключевой компонент — иерархическая radial/sunburst-визуализация.

Не использовать обычный одноуровневый PieChart как замену.

Структура:

```text
user
 ├── Documents
 │    ├── project1
 │    └── project2
 ├── Downloads
 └── Music
```

должна отображаться концентрическими уровнями.

---

# 21. Правила Sunburst

Центр:

- текущая выбранная папка.

Первое кольцо:

- непосредственные дочерние элементы.

Следующие кольца:

- последующие уровни вложенности.

Размер сектора:

- пропорционален занимаемому месту.

Большой каталог должен визуально иметь больший сектор.

---

# 22. Tooltip диаграммы

При наведении показывать:

```text
Название
Полный путь
Размер
Процент от родительской папки
Количество элементов
```

Пример:

```text
models

/Users/user/project/models

783 MB
38.1% папки project
```

---

# 23. Навигация через Sunburst

Клик по сектору папки должен позволять перейти внутрь.

Пример:

```text
user
→ project
→ models
```

После перехода одновременно меняются:

- центр диаграммы;
- Folder Browser;
- Column Browser;
- breadcrumb;
- размер;
- текущий контекст.

Не должно быть рассинхронизации между списком и диаграммой.

---

# 24. Выбор файлов и папок

Пользователь может выбрать один или несколько элементов.

Пример:

```text
☑ folder
☑ file
```

После выбора активируется нижняя action bar.

Пример:

```text
782.9 MB
Выбрано

1 элемент
```

Справа:

```text
Просмотреть и удалить ▼
```

---

# 25. Удаление

Удаление нельзя выполнять одним случайным кликом.

Рекомендуемый поток:

```text
Выбор
↓
Просмотреть и удалить
↓
Проверка
↓
Подтверждение
↓
Удаление
```

Перед удалением показать:

- имя;
- путь;
- размер;
- количество;
- действие.

Для нескольких объектов:

```text
Выбрано: 17 элементов
Размер: 4.6 ГБ
```

Если ОС позволяет безопасное удаление в корзину — предпочтительно использовать его.

---

# 26. Режим «Большие файлы»

Должен показывать самые крупные файлы независимо от каталога.

Пример:

```text
Название       Путь                       Размер
model.bin      ~/project/models           3.2 GB
archive.zip    ~/Downloads                 2.7 GB
video.mov      ~/Movies                    1.8 GB
```

Минимальная сортировка:

```text
Размер ↓
Размер ↑
Название
```

Желательно также:

- тип;
- дата изменения;
- путь.

---

# 27. Маленькие и скрытые элементы

Допускаются агрегированные группы:

```text
▶ Маленькие элементы        315 KB
▶ Скрытые элементы          8.48 GB
```

Они должны строиться только на реальных данных.

Пользователь должен иметь возможность раскрыть содержимое.

---

# 28. Поиск

Поиск должен работать по текущему контексту или по результатам сканирования.

Поведение должно быть понятно пользователю.

Минимально:

- поиск по имени;
- возможность очистить запрос;
- явное отсутствие результатов.

При большом наборе данных поиск не должен блокировать UI.

---

# 29. Состояния компонентов

Для интерактивных элементов обязательны:

```text
normal
hover
pressed
selected
disabled
focus
```

Не использовать только два состояния «синяя/серая».

---

# 30. Анимации

Допускаются короткие анимации:

```text
150–250 ms
```

для:

- hover;
- selection;
- раскрытия;
- смены режима;
- перехода по диаграмме.

Анимации не должны ухудшать производительность.

---

# 31. Иконки

Использовать один согласованный набор.

Не смешивать без необходимости:

- emoji;
- случайные системные bitmap;
- несколько icon packs;
- текстовые Unicode-символы.

Минимальный набор:

```text
Home
Disk
Folder
File
Applications
Downloads
Search
Back
Chevron
Help
Info
Delete
Refresh
```

---

# 32. Размеры и адаптивность

Целевая ширина:

```text
1200–1800 px
```

Интерфейс должен корректно работать на меньших окнах.

При уменьшении:

- sidebar остается читаемым;
- диаграмма масштабируется;
- file browser не исчезает;
- текст не накладывается;
- кнопки не выходят за границы;
- допускается scroll.

UI нельзя верстать только под один screenshot.

---

# 33. Производительность

Это критическое требование.

Интерфейс должен оставаться отзывчивым при:

```text
100 000+
500 000+
1 000 000+
```

элементов.

Не создавать UI-компонент для каждого найденного файла, если это приводит к деградации.

Использовать по необходимости:

- virtualization;
- lazy loading;
- incremental rendering;
- pagination;
- caching;
- aggregation;
- background workers;
- batching.

---

# 34. UI thread

Сканирование не должно блокировать UI thread.

Во время долгих операций приложение обязано:

- продолжать перерисовку;
- реагировать на перемещение окна;
- отображать progress;
- реагировать на cancel;
- не показывать системный статус «Not Responding».

---

# 35. Архитектурное разделение

Рекомендуемая модель:

```text
Scanner
    ↓
Filesystem Model
    ↓
Aggregation
    ↓
Application State / ViewModel
    ↓
UI
```

Не помещать файловое сканирование непосредственно в визуальные компоненты.

Folder Browser, Column Browser и Sunburst должны работать от одного состояния.

---

# 36. Компонентная структура

Рекомендуемая декомпозиция:

```text
AppShell
Sidebar
SidebarSection
SidebarItem
```

# 38. Ошибки и пустые состояния

Каждое состояние должно иметь нормальный UI.

Примеры:

```text
Папка пуста
```

```text
Нет доступа к папке
```

```text
Не удалось прочитать часть файлов
```

```text
Диск был отключен
```

Ошибка не должна выглядеть как crash или raw exception.

# 39. Accessibility

Минимальные требования:

- tooltip не должен быть единственным способом получить важную информацию;

# 41. Обязательная визуальная проверка

Компиляция не является достаточным критерием готовности UI.

После каждого крупного этапа:

```text
1. Запустить приложение
2. Открыть реализованный экран
3. Сделать screenshot
4. Сравнить с референсом
5. Найти визуальные отличия
6. Исправить
7. Повторить
```

Проверять:

- ширину sidebar;
- размеры областей;
- расположение диаграммы;
- размеры шрифтов;
- отступы;
- вертикальное выравнивание;
- высоту строк;
- радиусы;
- контраст;
- состояние selected;
- положение primary action;
- breadcrumb;
- нижнюю action bar.

---

# 42. Правило визуального соответствия

Основной критерий:

новый UI должен визуально быть ближе к приложенным референсам, чем к старой версии приложения.

Если после изменений:

- layout практически тот же;
- старая структура узнается сильнее референса;
- изменены в основном цвета;

редизайн считается незавершенным.

---

# 43. Запрет на фиктивную реализацию

Нельзя:

- рисовать статическую Sunburst;
- подставлять фиктивные размеры;
- показывать mock-файлы;
- оставлять неработающие кнопки;
- создавать декоративные вкладки;
- делать demo-only экран;
- подключать fake state вместо реального файлового дерева.

Все элементы должны быть связаны с реальными данными приложения.

---

# 44. Regression

Перед редизайном нужно зафиксировать существующие функции.

После редизайна проверить, что не потеряны:

- сканирование;
- навигация;
- работа с папками;
- работа с дисками;
- отображение размеров;
- удаление;
- поиск, если уже был;
- фильтрация;
- сортировка;
- настройки;
- иные существующие функции.

Если функция существует в старом интерфейсе, но отсутствует на референсе, она должна быть перенесена в логичное место нового UI.

---

# 45. Definition of Done

Редизайн считается завершенным только если одновременно выполнены все условия.

## 45.1. Функциональность

Все основные функции работают на реальных данных.

## 45.2. Архитектура

UI отделен от файлового сканирования и не превращен в монолит.

## 45.3. Производительность

Приложение остается отзывчивым на больших каталогах.

## 45.4. Визуальное соответствие

Интерфейс следует композиции и стилю референсов.

## 45.5. Навигационная целостность

Folder Browser, Breadcrumb и Sunburst синхронизированы.

## 45.6. Безопасность действий

Удаление требует явного подтверждения.

## 45.7. Визуальная проверка

Создан и проверен реальный screenshot финального UI.

# 46. Инструкция для CODEX

Перед любыми крупными изменениями UI:

1. Прочитать `UI_DESIGN_SPEC.md`.
2. Проанализировать текущую архитектуру.
3. Не использовать старый UI как визуальную основу.
4. Сохранить существующую бизнес-логику.
5. Реализовать новый layout.
6. Проверить приложение на реальных данных.
7. Сделать screenshot.
8. Сравнить с референсом.
9. Исправить отклонения.
10. Только после этого считать задачу выполненной.

# 47. Ключевая инструкция

> Не адаптируй существующий внешний вид минимальными изменениями. Считай текущий интерфейс временным. Сохрани бизнес-логику и модели данных, но пользовательский интерфейс разрешается и требуется перестроить полностью.

---

# 48. Финальный критерий

Если пользователь открывает новую версию приложения и при первом взгляде видит практически тот же интерфейс, что был раньше, задача выполнена неправильно.

Новый UI должен явно демонстрировать:

- новую структуру;
- новый Sidebar;
- новый Content Area;
- новый Folder Browser;
- новую Sunburst-визуализацию;
- новую action bar;
- новую визуальную иерархию;
- новый подход к навигации.

При этом функциональность должна оставаться рабочей.
